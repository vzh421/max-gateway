# Этап 1 — каркас

Статус: **каркас готов, проверен локально** (98 тестов на SQLite и PostgreSQL 16, сборка образа,
запуск стека Docker Compose без сессии MAX, команды CLI в контейнере). С реальным MAX
каркас ещё не запускался.

## Что сделано

| Часть | Где |
|---|---|
| Конфиг из `.env`, безопасные значения по умолчанию | `gateway/config.py`, `.env.example` |
| БД и миграции (PostgreSQL, Alembic) | `gateway/db/`, `gateway/migrations/` |
| Интерфейс транспорта + PyMax, заглушки Fake и Green API | `gateway/transport/` |
| Единая точка отправки с правилами 1, 5, 6, 8, 9 | `gateway/safety.py` (`SendGuard`, `KillSwitch`) |
| Мониторинг соединения, уведомления (пока в лог) | `gateway/monitor.py` |
| Журнал входящих с идемпотентностью | `gateway/journal.py` |
| Импорт телефонов из CSV, белый список | `gateway/importers.py` |
| Служебный API: `/health`, `/admin/*` | `gateway/api.py` |
| CLI: `python -m gateway …` | `gateway/__main__.py` |
| Docker Compose: `gateway` + `db` | `Dockerfile`, `docker-compose.yml` |

На этапе 1 шлюз только записывал входящие в журнал. Сценарий S1 — [stage2.md](stage2.md).

## Решения

- **PostgreSQL**, а не SQLite. Лимиты, cooldown и идемпотентность держатся на транзакциях
  и уникальных ключах. Бот и шлюз пишут в одну БД. Тесты идут на обеих СУБД.
- ~~Бот в том же процессе~~ — **пересмотрено на этапе 2**: бот ведётся в отдельной
  сессии, связь по HTTP ([bot-integration.md](bot-integration.md)).
- **`case_id` — строка.** Тип id дел в ai4au не сверен: доступа к API из среды разработки
  не было.

## Как устроены защитные правила

`SendGuard.send()` — единственный путь отправки с личного аккаунта. Тест проверяет, что
`send_text`/`send_message` не вызываются нигде вне `gateway/safety.py` и `gateway/transport/`.

Проверки идут по порядку. Каждая попытка, в том числе заблокированная, пишется в `message_log`.
1. **Kill switch** (правило 8): `KILL_SWITCH=true` или файл-флаг `/data/KILL_SWITCH`.
   Файл проверяется при каждой отправке — включение действует сразу, без перезапуска.
   `python -m gateway kill on|off|status` или `POST /admin/kill-switch`.
2. **Блокировка мониторингом** (правило 9): разрыв, слёт сессии или ошибка библиотеки
   записывают блокировку в БД и шлют одно уведомление. **Переподключение блокировку не снимает** —
   только `python -m gateway sends resume` после разбора причины.
3. **Неутверждённый текст**: пока в тексте есть `[НЕ УТВЕРЖДЕНО]`, боевая отправка запрещена.
4. **Никаких рассылок первым** (правило 5): в чат, из которого не было входящего, не пишем.
5. **Лимит перенаправлений на чат** (правило 5; на этапе 2 заменил cooldown 30 дней —
   см. [stage2.md](stage2.md)).
6. **Лимит в час** — `MAX_REPLIES_PER_HOUR` (правило 6).
7. **Dry-run** (правило 1): только запись «отправил бы».
   Перед боевой отправкой идёт случайная задержка `REPLY_DELAY_SEC`, после неё пункты 1–2
   проверяются ещё раз. Журналы dry-run и боевого режима считаются раздельно: история
   dry-run не блокирует боевые ответы.

Прочее:
- **Правило 7 (не отмечать прочитанным):** в интерфейсе транспорта такого метода нет.
  `MARK_READ=true` не даст сервису запуститься. Тест проверяет, что в коде нет
  вызовов `read()` / `read_message`.
- **ПДн в логах:** фильтр на корневом логгере маскирует телефоны, ИНН и СНИЛС, в том числе
  в логах PyMax. `LOG_LEVEL=DEBUG` запрещён: на DEBUG PyMax пишет токен сессии.
- **Сессия MAX:** volume `/data/session`, каталог 700, файлы 600. Права выставляются при
  каждом подключении. Файл сессии в образ не попадает (`.dockerignore`).
- **Падение транспорта не завершает процесс.** Иначе Docker перезапускал бы контейнер и
  переподключал личный аккаунт в цикле. Транспорт после падения сам не перезапускается.
  API остаётся доступен, `/health` показывает `sends_blocked: true`.
- **Отозванная сессия:** в режиме `run` SMS-вход не запрашивается никогда
  (`RefuseAuthFlow`). SMS — только команда `login`.

## Белый список из адресной книги

По журналу этапа 0: на восстановленной сессии MAX отдаёт только изменения контактов.
Поэтому:
- `python -m gateway login` — первый вход по SMS. Контакты, которые вернул MAX, сразу
  уходят в белый список (`source=address_book`), импорт отмечается в `app_state`.
- `python -m gateway contacts-sync` — вход по существующей сессии с принудительным маркером
  синхронизации контактов `-1` (начальное значение у новой сессии). **Отдаст ли сервер
  при этом полный список — не проверено.**
- Пустой ответ импортом не считается: пустота не значит «контактов нет».
- Ручное добавление: `python -m gateway whitelist add +7…`.

## Импорт телефонов должников

CSV с заголовком: `case_id`, `phone`, необязательно `note`. Разделитель `,` / `;` / Tab,
кодировка UTF-8 или Windows-1251. Номера приводятся к виду `7XXXXXXXXXX`, дубли пропускаются,
строки с ошибками перечисляются в отчёте (номера маскированы).

```bash
python -m gateway import-phones phones.csv
```

Второй способ — `POST /admin/debtor-phones` с заголовком `X-Admin-Token`.

## Что не проверено

- Работа каркаса с реальным MAX: `login`, `contacts-sync`, `run` с живой сессией.
- Отдаёт ли `contacts-sync` полный список контактов.
- Как часто в реальности будут разрывы. Каждый разрыв блокирует отправки до ручного
  `sends resume`. Если это окажется слишком часто, правило можно смягчить: например,
  автоматически снимать блокировку после короткого разрыва. Решает управляющий.
- Поля и тип id в ai4au.
