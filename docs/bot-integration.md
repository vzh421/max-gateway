# Контракт шлюза max-gateway с официальным ботом MAX

Документ для сессии, которая разрабатывает официального бота MAX (ООО «Бурсофт»).
Шлюз (этот репозиторий) работает на личном номере управляющего Жалсанова В.В.: узнаёт
должника по телефону и перенаправляет его в бот ссылкой с одноразовым токеном. Всё, что
происходит в боте (согласие на обработку ПДн, привязка, ответы), делает бот.

Версия контракта: **v1**. Изменения — только по согласованию обеих сессий.

## 1. Что присылает шлюз должнику

Первое сообщение, затем не больше 3 мягких напоминаний, не чаще раза в сутки. Во всех
сообщениях одна и та же ссылка, пока токен действует.

```
https://max.ru/<BOT_USERNAME>?start=<token>
```

- `token` — **32 символа `[0-9a-f]`** (128 бит). Это подмножество допустимого алфавита
  payload: латиница, цифры, `-`, `_`, до 128 символов.
- Если токен этого чата уже погашен ботом, в напоминании ссылка **без `start`**:
  `https://max.ru/<BOT_USERNAME>`. Должник уже в боте, бот узнаёт его по своему user_id.
- Не проверено (dev.max.ru из среды разработки шлюза недоступен): формат deep link и
  то, что payload приходит в поле `payload` события `bot_started`. Это взято из CLAUDE.md
  проекта, сверить по документации MAX на стороне бота.

## 2. API шлюза для бота

Базовый адрес — см. раздел 4. Все запросы — с заголовком `X-Api-Key: <BOT_API_KEY>`
(общий секрет в `.env` обеих сторон). Без ключа или с неверным ключом — `401`. Если
ключ не задан в шлюзе — `503`.

### 2.1. Проверить токен (не гасит)

`GET /bot-api/v1/tokens/{token}`

Ответ `200`:
```json
{
  "status": "valid",
  "case_id": "A40-1234/2025",
  "candidate_case_ids": [],
  "expires_at": "2026-10-10T09:00:00+00:00",
  "used_at": null
}
```

- `status`: `valid` | `used` | `expired`. Неизвестный или некорректный токен — `404`.
- `case_id` — id дела в ai4au (строка), если номер найден ровно в одном деле.
- `candidate_case_ids` — если номер телефона найден в **нескольких** делах: `case_id = null`,
  выбор дела — в боте.
- `case_id = null` и пустой `candidate_case_ids` — дело не определено (включается только
  при `REPLY_TO_UNKNOWN=true`; по умолчанию таким не отвечаем).

### 2.2. Погасить токен

`POST /bot-api/v1/tokens/{token}/redeem`
```json
{"bot_user_id": 123456, "bot_chat_id": 7890}
```

| Код | Когда | `redeemed_now` |
|---|---|---|
| `200` | Токен погашен этим вызовом | `true` |
| `200` | Повтор тем же `bot_user_id` (идемпотентно) | `false` |
| `409` | Уже погашен **другим** пользователем | `false` |
| `410` | Истёк (`TOKEN_TTL_DAYS`, по умолчанию 14 дней) | `false` |
| `404` | Нет такого токена / неверный формат | `false` |

Тело ответа — как в 2.1 плюс `redeemed_now`. Гашение атомарное: из параллельных вызовов
успешен ровно один.

Рекомендуемый порядок в боте (решает сессия бота): `bot_started(payload)` → `GET` (показать,
что ссылка действительна) → согласие на ПДн → `redeem` → привязка у себя. При `409`/`410`/`404` —
сценарий «невалидный токен» (CLAUDE.md, S2 п. 4).

## 3. API бота для шлюза: уведомления управляющему

Шлюз отправляет уведомления управляющему **через бота**:

`POST <BOT_NOTIFY_URL>` с заголовком `X-Api-Key: <BOT_NOTIFY_KEY>`
```json
{"kind": "unknown", "urgent": false, "text": "Пишет неизвестный (7********67), чат 116679694. Автоответа нет."}
```

- Ожидаемый ответ — любой `2xx`. При ошибке шлюз пишет уведомление в свой лог и
  продолжает работу (повторов нет).
- `urgent: true` — отправляется сразу (сбой соединения с MAX, отправки остановлены).
  Несрочные шлюз собирает и присылает сводкой одним сообщением (`kind: "digest"`) раз в
  `NOTIFY_DIGEST_MINUTES` (по умолчанию 60).
- `text` — готовый текст на русском. Телефоны, ИНН и СНИЛС в нём уже маскированы.
- `kind` (информационно): `monitor`, `digest`, а внутри сводки события: `unknown`,
  `whitelist_match`, `redirect_first`, `redirect_reminder`, `redirect_limit`, `error`, `config`,
  `contacts_review` (новые спорные контакты), `contacts_error` (сбой синхронизации контактов).
- Кому в боте доставлять (id чата управляющего) — решает сессия бота.

## 4. Сеть

Шлюз публикует API на `127.0.0.1:${GATEWAY_API_PORT}` сервера (по умолчанию 8090) и в
контейнере слушает `:8080`. Варианты (выбрать при развёртывании):

1. **Бот в Docker на том же сервере** — общая внешняя сеть:
   ```bash
   docker network create max-net
   docker compose -f docker-compose.yml -f docker-compose.botnet.yml up -d   # в max-gateway
   ```
   Шлюз доступен боту как `http://max-gateway:8080`. Бот подключает свой сервис к сети
   `max-net`, и тогда `BOT_NOTIFY_URL=http://<имя-сервиса-бота>:<порт>/<путь>`.
2. **Бот на хосте без Docker** — `http://127.0.0.1:8090`.

Наружу (в интернет) API шлюза не публикуется.

## 5. Что шлюз НЕ делает

- Не пишет в бот и не читает его события.
- Не хранит согласие на ПДн и привязки бота (таблица `bot_bindings` в схеме шлюза
  зарезервирована и не используется).
- Не вызывает изменяющие методы ai4au.
