# max-gateway — шлюз MAX для общения с должниками

## Назначение

Сервис для арбитражного управляющего Жалсанова В.В. (~1000 должников, 1055 дел в ai4au).
Задача — снять с управляющего ручную переписку с должниками в MAX:

1. **Шлюз личного аккаунта** (userbot на основном номере управляющего). Когда должник пишет
   в личный MAX, шлюз узнаёт его по номеру телефона и один раз отвечает ссылкой на
   официального бота с одноразовым токеном.
2. **Официальный бот MAX** (зарегистрирован на ООО «Бурсофт»). По токену привязывает чат
   к делу; дальше всё общение с должником идёт в боте.

Язык интерфейса, сообщений, комментариев в коде и документации — русский.

## ВАЖНО: шлюз работает на ОСНОВНОМ личном номере управляющего

На этом номере жена, коллеги, суды, кредиторы. Блокировка номера = потеря личного MAX.
Поэтому защитные правила ниже — обязательные, не опциональные, и покрываются тестами.

1. **Режим по умолчанию — `DRY_RUN=true`.** В dry-run шлюз ничего не отправляет, только
   пишет в журнал, что отправил бы. Боевой режим включается только явно через `.env`.
2. **Отвечать только сопоставленным должникам.** Автоответ уходит, только если номер
   отправителя найден в реестре телефонов должников. Неизвестные номера — только запись
   в журнал и уведомление управляющему. Параметр `REPLY_TO_UNKNOWN=false` по умолчанию.
3. **Белый список.** Контакты, существовавшие в адресной книге аккаунта на момент первого
   запуска, плюс ручной список — никогда не получают автоответ, даже если номер совпал
   с должником (сначала уведомить управляющего).
4. **Только личные чаты.** Группы, каналы, боты — игнорировать.
5. **Одна ссылка на чат.** Повторный автоответ тому же чату — не раньше `REPLY_COOLDOWN_DAYS`
   (по умолчанию 30). Никаких рассылок первым с личного аккаунта — никогда.
6. **Лимит частоты.** Не более `MAX_REPLIES_PER_HOUR` (по умолчанию 10) автоответов в час
   суммарно; случайная задержка перед ответом `REPLY_DELAY_SEC` (по умолчанию 20–90 с).
7. **Не отмечать чаты прочитанными** (`MARK_READ=false`), чтобы управляющий не пропустил
   сообщения в своём приложении.
8. **Аварийный выключатель.** Файл-флаг или переменная `KILL_SWITCH`, мгновенно
   останавливающая любые отправки с личного аккаунта без остановки приёма.
9. **Мониторинг.** Если соединение с MAX упало/сессия слетела/библиотека вернула
   неожиданную ошибку — уведомление управляющему (через бота) и остановка отправок.

## Архитектура

```
Должник ──► личный MAX управляющего
                 │ (события через неофициальный протокол)
                 ▼
        ┌──────────────────┐     чтение дел/должников     ┌─────────┐
        │ userbot-адаптер  │ ───────────────────────────► │ ai4au   │
        └────────┬─────────┘      (HTTP API ai4au)        │ backend │
                 │                                         └─────────┘
                 ▼
        ┌──────────────────┐
        │  core (логика)   │  сопоставление, токены, правила, журнал
        │  + БД сервиса    │
        └────────┬─────────┘
                 ▲
                 │ bot_started(payload=токен), сообщения
        ┌──────────────────┐
        │  bot-адаптер     │ ◄── официальный MAX Bot API
        └──────────────────┘
```

Ключевой принцип — **слой-адаптер**. Логика (`core`) не знает, как подключён личный
аккаунт. Интерфейс `PersonalAccountTransport` с реализациями:
- `PyMaxTransport` — свой шлюз (основная реализация);
- `GreenApiTransport` — заглушка-резерв на случай, если свой шлюз сломается или будет
  заблокирован (реализовать позже, но интерфейс проектировать под неё).

### Сервисы (Docker Compose)
- `gateway` — userbot + core (один процесс, asyncio).
- `bot` — webhook/long polling официального бота (может жить в том же процессе — решить
  на этапе 1, обосновать).
- `db` — PostgreSQL (или SQLite на старте — обосновать выбор).

Деплой — рядом с ai4au на VPS Beget (там же Docker Compose и nginx).

## Технологии (проверено по документации, но ВЕРСИИ И API СВЕРИТЬ ПЕРЕД НАЧАЛОМ)

- Python 3.11+, asyncio, FastAPI (для служебных эндпоинтов и webhook бота), SQLAlchemy/Alembic.
- **Userbot:** `maxapi-python` (PyMax, репозиторий MaxApiTeam/PyMax). Авторизация по
  телефону и SMS-коду, сессия сохраняется в SQLite-файл, соединение TCP или WebSocket.
  Библиотека неофициальная, API между версиями менялся (имена классов клиента отличаются
  в разных форках/версиях). **Зафиксировать точную версию, читать её документацию и
  исходники, не угадывать сигнатуры.** Альтернатива для сравнения: `maxion` (userbot +
  официальный Bot API в одной библиотеке). На этапе 0 сравнить обе и выбрать.
- **Официальный бот:** MAX Bot API. Актуальный домен и методы сверить на dev.max.ru
  (в открытых источниках встречаются `platform-api.max.ru`, устаревший `botapi.max.ru`
  и `platform-api2.max.ru` — проверить, какой верный).
- **Deep link бота:** `https://max.ru/<ник_бота>?start=<payload>`. Payload приходит в поле
  `payload` события `bot_started`. Ограничения: до 128 символов, только латиница, цифры,
  `-` и `_`. Если у бота активна подписка на webhook, long polling событий не получает.

## Интеграция с ai4au (боевая система — только чтение без явного согласия)

ai4au — FastAPI backend, `https://ai4au.ru`. Известные эндпоинты:
- `GET /api/v1/cases/` — список дел (поля: `id`, `case_number`, `debtor_name`,
  `procedure_type_code`, `status`, `court_name`, `expected_completion_date` и др.; есть `total`).
- `GET /api/v1/cases/{case_id}/debtor` — карточка должника (`full_name`, `inn`, `snils`,
  `birth_date`, `attributes_jsonb`).
- `PUT /api/v1/cases/{case_id}/debtor` — upsert карточки (НЕ вызывать без согласования).

**Телефонов должников в ai4au сейчас нет.** Поэтому в сервисе своя таблица
`debtor_phones` (case_id, phone в формате 7XXXXXXXXXX, источник, дата). Заполнение:
импорт CSV + служебный эндпоинт. Перенос телефонов в ai4au — отдельное решение позже.

Любые изменяющие вызовы ai4au (POST/PATCH/PUT/DELETE) — только после явного
подтверждения управляющего.

## Модель данных (черновик, уточнить на этапе 1)

- `debtor_phones` — телефоны должников, связь с case_id ai4au.
- `whitelist` — номера/chat_id, которым автоответ запрещён (+ источник: адресная книга / ручной).
- `personal_chats` — chat_id личного аккаунта ↔ телефон ↔ case_id, дата последнего автоответа.
- `link_tokens` — одноразовый токен → case_id, создан, истекает (`TOKEN_TTL_DAYS`, по умолч. 14),
  использован (кем, когда). Токен криптостойкий (`secrets.token_urlsafe`), в пределах
  128 символов и допустимого алфавита.
- `bot_bindings` — user_id/chat_id в боте ↔ case_id, дата привязки, согласие на обработку ПДн.
- `message_log` — все входящие/исходящие (канал: personal/bot, направление, текст,
  вложения, case_id если известен, признак dry-run).

## Сценарии

### S1. Должник пишет в личный MAX
1. Событие входящего сообщения → фильтр: только личный чат, не свой исходящий.
2. Записать в `message_log` всегда.
3. Нормализовать телефон отправителя (если скрыт/недоступен — считать «неизвестным»).
4. Белый список → стоп, без ответа.
5. Поиск в `debtor_phones`:
   - найден ровно один case_id → проверка cooldown и лимитов → выпуск токена →
     автоответ со ссылкой на бота (текст шаблона — из конфигурации, утверждает управляющий);
   - найдено несколько дел → токен на выбор дела в боте (или уведомить управляющего — решить);
   - не найден → уведомление управляющему, без ответа (если `REPLY_TO_UNKNOWN=false`).
6. Уведомление управляющему о каждом автоответе (сводкой, не спамом).

### S2. Должник открывает бота по ссылке
1. `bot_started` с payload → проверить токен (существует, не истёк, не использован).
2. Показать запрос согласия на обработку персональных данных (текст утверждает
   управляющий — не сочинять юридические формулировки, оставить плейсхолдер).
3. После согласия — создать `bot_bindings`, погасить токен, приветствие с ФИО и номером дела.
4. Токен невалиден → предложить написать номер дела и дату рождения → заявка на ручную
   привязку управляющему (автопривязки по этим данным нет).

### S3. Бот без payload
То же, что невалидный токен в S2.

### S4 (этап 3+). Ответы бота
Статус дела из ai4au, дата ближайшего заседания, список непредоставленных документов,
приём файлов. Ответы на юридические вопросы — только черновик на одобрение управляющему,
никакой автоматической отправки.

## Безопасность

- Файл сессии userbot = полный доступ к личному аккаунту: хранить вне репозитория,
  в volume с правами 600, в `.gitignore`, не логировать, не копировать в образы.
- Секреты (токен бота, токен ai4au, телефон) — только в `.env`, в репозиторий — `.env.example`.
- Персональные данные должников в логах приложения — маскировать (телефон, ИНН, СНИЛС).
  Полные данные — только в БД.
- Первая авторизация userbot (ввод SMS-кода) — интерактивно, отдельной командой
  (`python -m gateway login`), управляющим лично.

## Этапы

**Этап 0 — разведка (без отправок).** Сравнить PyMax и maxion на актуальных версиях:
авторизация, получение входящих (какие поля отправителя, приходит ли телефон),
отправка, чтение контактов. Прототип, который только ПЕЧАТАЕТ входящие события.
Результат — короткий отчёт в `docs/stage0.md` с выбором библиотеки и реальной структурой событий.

**Этап 1 — каркас.** Репозиторий, Docker Compose, БД и миграции, конфиг, интерфейс
транспорта, журнал, dry-run, kill switch, импорт телефонов из CSV, белый список из
адресной книги.

**Этап 2 — S1 + S2 + S3** в dry-run → тест на 5–10 своих должниках в боевом режиме
по явному решению управляющего.

**Этап 3 — полезные ответы бота** (S4) с данными ai4au.

## Критерии готовности этапа 2

- Все защитные правила покрыты тестами (белый список, cooldown, лимит, dry-run,
  kill switch, группы игнорируются, неизвестные не получают ответ).
- Повторное событие о том же сообщении не приводит к повторному ответу (идемпотентность).
- Токен нельзя использовать дважды; просроченный отклоняется.
- Падение соединения с MAX даёт уведомление и останавливает отправки.
- В логах нет полных телефонов/ИНН/СНИЛС.

## Правила работы для Claude Code

- Ничего не придумывать: форматы событий, методы библиотек и Bot API — только по
  документации/исходникам зафиксированной версии или по реально полученным данным.
  Если не удалось проверить — написать об этом, а не угадывать.
- Никаких отправок с личного аккаунта во время разработки без явного разрешения
  управляющего в чате. Для разработки — dry-run и тестовые моки транспорта.
- Никаких изменяющих вызовов к боевому ai4au без явного подтверждения.
- Тексты сообщений должникам и юридические формулировки — плейсхолдеры в конфиге,
  утверждает управляющий.
